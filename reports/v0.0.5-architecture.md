# Архитектура и визуальный разбор v0.0.5beta

Исходный план и PNG прочитаны из коммита 58f33a8. Это рабочий документ реализации, не заявление о готовности функций.

## Что задано изображениями

Светлая тема: фон #F6F8FC, карточки #FFFFFF, основной текст #152238 и дополнительный #52617A. Тёмная: #0E1923, #192631, #F2F6FA и #B5C5D8. Основной акцент #007AFF; для тёмной темы нужен более светлый вариант текста/обводок с проверяемым контрастом. Белый текст на исходном #007AFF требует проверки контраста; цвет основной кнопки можно немного затемнить для читаемости.

Карточки 16dp, диалоги 20dp, поля/основные отступы 16dp, touch targets от 48dp. Типографика соответствует системному масштабированию. Одна большая кнопка входа; брендинг из утверждённого app-icon-source.png. Мелкие ошибки букв в PNG не переносятся в приложение.

Верхний уровень — Мои боты / Консоль / Профиль. Внутри Консоли остаются Бот / Сообщение / События. Обзор показывает реальные значения текущей сессии; сообщения сохраняются как шаблоны только по явному действию. Избранный получатель всегда проверяется заново. Списки не содержат демонстрационные имена или ненадёжные нулевые счётчики.

## Вход и полный список принадлежащих аккаунту ботов

Официальный источник найден: [bots.getAdminedBots](https://core.telegram.org/method/bots.getAdminedBots) возвращает ботов текущего владельца и доступен только пользовательской Telegram API-сессии. В TDLib есть [getOwnedBots](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1get_owned_bots.html). Обычный Login/OIDC не является такой сессией.

Предлагаемая архитектура сохраняет две отдельные части:

1. Официальный native Telegram Login / OIDC для профиля Hunmeng Console. Сервер создаёт state/nonce/PKCE, проверяет callback, обменивает code, проверяет подпись, issuer, audience и сроки ID token, предотвращает replay. Client Secret только на сервере. Подписанный сервером/проверенный профиль привязан к стабильному Telegram ID; username для отображения.
2. Отдельно явно обозначенный клиентский доступ через TDLib на телефоне для getOwnedBots. Его не выдавать за разрешение обычного Login. Нужны API-приложение my.telegram.org и отдельное подтверждение Telegram-клиентской сессии. Этот доступ способен читать аккаунтные данные; приложение использует список ботов, доступных чатов и роль бота, без автоматической отправки сообщений.
3. Владелец выбрал сохранение зашифрованной сессии на телефоне с удалением при выходе. TDLib использует приватный каталог Android и случайный ключ шифрования; ключ хранится обёрнутым AES-GCM ключом Android Keystore, backup отключён. Базы сообщений и файлов отключены; выход отзывает сессию и удаляет каталог и локальные секреты. Сессию можно отозвать в Telegram → Настройки → Устройства.
4. После Login сразу открыть Мои боты. Пока источник TDLib не авторизован, показывать Источник не подключён, а не пустой список. Проверенный TDLib getMe должен совпадать с ID профиля Login.
5. Подключение Bot API-токеном не считается доказательством владения. Для выбранного принадлежащего аккаунту бота getMe должен вернуть именно его ID; токен остаётся только в памяти. Открытие консоли не запускает polling и не отправляет сообщения.

## Каналы и группы

[getChatMember](https://core.telegram.org/tdlib/docs/classtd_1_1td__api_1_1get_chat_member.html) подтверждает роль конкретного бота в доступном чате. getGroupsInCommon даёт общие группы, а не все каналы бота. Для каналов требуется перебрать доступные пользовательской сессии каналы и отдельно проверить участника bot ID. Это подтверждает связи в доступных аккаунту чатах; не доказывает полноту всех чужих/недоступных чатов, в которые кто-либо добавил бота.

UI должен называть результат Доступные каналы и группы и явно отмечать охват. Отдельно сохраняется неизвестный/недоступный результат проверки; ошибка не превращается в отсутствие чата. Полный список ботов из getOwnedBots не подменяется списком подключённых токенов.

## Native Login SDK

[Официальный SDK](https://github.com/TelegramMessenger/telegram-login-android) поддерживает minSdk 23, проект имеет minSdk 26. Изученный SDK 1.0.0 не предоставляет state/nonce и обменивает code на устройстве; его пример предлагает логировать ID token. Такой пример несовместим с требованиями плана. Интеграция должна адаптировать native intent-flow к серверному state/nonce/PKCE и обмену; credential/JWT не логируются. Зависимость не должна требовать публикации GitHub PAT в исходники.

## Подпись и обновления

Старые сертификаты несовместимы между собой; доступный локальный debug-ключ не совпадает с ними. Для v0.0.5 нужен постоянный ключ следующих выпусков с приватной резервной копией. Первичная установка на старую подпись не становится возможной. Удаление установленного приложения без команды владельца не выполняется.

Источник обновления должен указывать Android package, versionCode, SHA-256, сертификат, фактические возможности и точный HTTPS asset из этого GitHub-репозитория. Позже запоминается по ID выпуска с интервалом; Что нового — один раз для установленной версии. При несовместимой подписи установка не запускается автоматически.

## Необходимая конфигурация

Для реального native Login понадобятся выбранный бот-приложение, client_id, серверный Client Secret, разрешённый callback и SHA-256 сертификата в BotFather. Для TDLib — API-приложение my.telegram.org. Секреты не передаются в чате и не сохраняются в репозитории; места конфигурации и развёртывание будут указаны после выбора архитектуры.

Существующий веб-backend Hunmeng Console проверяется отдельно: пригодность маршрутов авторизации и хранилища нельзя предполагать по наличию опубликованного сайта.
